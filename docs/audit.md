### processor.py

**Purpose:** STEP 1 — image preparation and segmentation. STEP 2 — Zero123++ novel-view
synthesis. STEP 3 — DepthAnything depth estimation.

**Key functions:**
- load_zero123() — lazy global; loads sudo-ai/zero123plus-v1.2 diffusion pipeline
- load_depth() — lazy global; loads LiheYoung/depth-anything-large-hf via HF pipeline
- load_rembg() — lazy global; loads rembg isnet-general-use session
- warmup() — loads rembg at startup; optionally loads heavy models
- elease_zero123() / elease_depth() / elease_models() — set globals to None + empty_cache
- _clean_mask(alpha_arr) — morphological mask cleaning (MinFilter×2, label, MaxFilter×3, Gaussian)
- subject_crop(img_rgba, pad_frac) — tight crop + square pad
- _sharpen_rgb(img_rgb, amount) — unsharp mask (gaussian sigma=1.0, amount=0.5)
- _match_view_color(view_rgb, ref_rgb, ref_mask) — Reinhard LAB transfer at 40% blend
- prepare_image(image_path, out_dir) — rembg → clean_mask → subject_crop → save masked.png
- _view_mask_rembg(rgb_pil) — per-view foreground mask via rembg
- _view_mask_corners(rgb_pil) — Otsu fallback background detection
- _zero123_tiles(grid) — validate grid 960×640 or 640×960; yield 6 (img, az, el) tiles
- generate_views(img_rgba, out_dir) — sharpen → 256px resize → Zero123++ 25 steps →
  color transfer → mask each view → save view_i.png / mask_i.png / view_poses.json
- _edge_guided_sharpen(depth, rgb) — Sobel-weighted blend raw/Gaussian-smoothed depth
- _colorize_depth(depth_norm) — turbo colormap
- estimate_depths(images, out_dir) — DepthAnything at 518px → normalize → sharpen →
  save depth_grey_i.png / depth_color_i.png
- _prepare_user_views(view_paths, img_rgba, out_dir) — user multiview path
- process_image(image_path, ...) — main pipeline: prepare → pose → views → depths → return dict

**Inline camera math:** NONE in processor.py. Camera math is fully in reconstructor.py.

**GPU management:**
- Zero123++ released after views if not KEEP_PROCESSOR_MODELS_WARM.
- DepthAnything released after depths if not KEEP_PROCESSOR_MODELS_WARM.
- _free_cuda() calls gc.collect() + empty_cache() + ipc_collect().

**Data passing:** Returns a plain dict with keys: status, out_dir, masked, views, depths_grey,
depths_color, time, stage_times, input_mode, target_dimensions_mm.

**Depth analysis (CRITICAL):**
- estimate_depths produces 7 depth maps (1 front + 6 views), normalizes each independently
  [0,1] via per-image min/max. This destroys cross-image scale relationships.
- The normalized depth arrays are SAVED to disk only (depth_grey_i.png, depth_color_i.png).
- NO depth array is returned from process_image. Only file paths are returned.
- econstructor._load_depth_maps reloads them from disk as normalized [0,1] float32 arrays.
- The loaded depth maps are explicitly documented as "relative" in reconstructor.py and
  are NOT used for metric voxel carving.
- CONCLUSION: Depth is generated, saved, reloaded, and then explicitly skipped for geometry.
  This is "Option B" behavior (depth isolated as diagnostic) but it happens by comment/logging
  rather than by enforced contract.

**Constants:**
- IMG_SIZE = 320 (view tile size)
- DEPTH_SIZE = 518 (DepthAnything native res)
- FG_ALPHA_THRESHOLD = 64 (env: TRIGENIX_FG_ALPHA_THRESHOLD)
- VIEW_POSES = [(30,20),(90,-10),(150,20),(210,-10),(270,20),(330,-10)] — 6 azimuths/elevations

### reconstructor.py

**Purpose:** Load views from out_dir, attempt reconstruction via InstantMesh → TripoSR →
MultiViewHull in that priority order, post-process mesh, paint vertex colors, export assets.

**Key functions:**
- _camera_c2w(az_deg, el_deg, dist) — camera-to-world rotation + position. DUPLICATES logic
  that does not exist in processor.py (processor has no camera math at all).
- _project(pts_world, az_deg, el_deg) — projects 3D points to 2D pixels. Used internally.
  FOV_DEG=36.9, CAM_DIST=1.80, IMG_SIZE=320.
- load_from_dir(out_dir) — loads views from disk as list of dicts (untyped)
- _get_mask(v) — mask extraction with 3 fallback priorities
- _load_depth_maps(out_dir, expected, size) — loads depth_grey_i.png as float32
- _improved_visual_hull(views, allow_fallback) — silhouette carving, marching cubes,
  GRID_RES=256, WORLD_HALF=0.65. Depth maps are loaded but explicitly NOT used for geometry.
- _create_sphere_fallback() — creates icosphere(subdivisions=3, radius=0.5)
- _mesh_is_usable(mesh, min_faces) — quality gate: min 1000 faces, finite bounds, aspect > 0.035
- paint_colors(mesh, views, base_colors) — vertex color painting: normal weight × center weight
  × FRONT_BOOST(5.0); second pass; kd-tree fill; edge-aware smoothing
- _detect_opening_masks(views) — dark interior detection for visual openings
- _preserve_visual_openings(mesh, views) — removes faces in opening regions from visual mesh
- cleanup(mesh, target_faces, smooth, keep_largest) — degenerate removal, decimation,
  Taubin smooth (but uses nu=0.20, spec says μ=-0.20 — sign discrepancy), repair
- _auto_orient(mesh) — PCA principal axis → Y-up alignment
- _orient_and_normalize(mesh, out_dir, target_dimensions_mm) — pose rotation → auto_orient
  → unit bbox normalize → scale to mm if specified
- _build_quality_report(mesh, method, ...) — builds quality dict (NOT the full QualityReport spec)
- _export_asset_profiles(mesh, out_dir, method, ...) — exports print_stl, print_glb, ar_vr,
  game, simulation, collision, writes quality_report.json
- econstruct_from_dir(out_dir, backend, ...) — main entry point
- _try_instantmesh(out_dir, views) — InstantMesh inference
- _try_triposr(out_dir) — TripoSR inference with resolution cascade
- _try_export_triposr_baked_glb(mesh, model, scene_code, out_dir) — UV texture baking

**Reconstruction fallback chain (backend='auto'):**
1. InstantMesh (only if _instantmesh_available() passes: CUDA + nvdiffrast + ckpt)
2. TripoSR (always attempted if InstantMesh fails/unavailable)
3. MultiViewHull / Sphere only if explicitly requested via backend param

**CRITICAL NOTE on auto mode:** When backend='auto' and InstantMesh is unavailable, the system
falls straight to TripoSR. MultiViewHull is never tried in auto mode. This means:
- "auto" = InstantMesh → TripoSR only (2 backends, not 3)
- The existing code comment in the file explicitly acknowledges this.

**Constants:**
- CAM_DIST = 1.80, FOV_DEG = 36.9 — camera placement for visual hull
- GRID_RES = 256, WORLD_HALF = 0.65 — voxel grid parameters
- TARGET_FACES = 100_000 — decimation target (spec says 50,000 — discrepancy)
- TRIPOSR_RESOLUTIONS = (320, 256, 224, 192, 160, 128) — resolution cascade

**Data passing:** Views passed as list of dicts with keys: rgb, rgb_raw, mask_path, az, el,
use_alpha, alpha_mask, view_idx, out_dir. No typed contracts.

**Validation:** No orthonormality check on the returned world_R (Ry@Rz is always orthonormal

## Bug Verification

### Bug A — Unguarded Sphere Fallback

**STATUS: CONFIRMED WITH NUANCE**

_create_sphere_fallback() exists (line ~160 of reconstructor.py):
`python
def _create_sphere_fallback():
    """Create a simple sphere as absolute last resort"""
    import trimesh
    mesh = trimesh.creation.icosphere(subdivisions=3, radius=0.5)
    logger.warning("  Using sphere fallback mesh")
    return mesh
`

It is called from _improved_visual_hull(views, allow_fallback=False) in three places:
1. if vol.sum() < 1000 and allow_fallback: return _create_sphere_fallback()
2. except: ... if allow_fallback: return _create_sphere_fallback()
3. if not _mesh_is_usable(mesh) and allow_fallback: return _create_sphere_fallback()

It is ALSO callable via econstruct_from_dir when ackend in ("sphere", "sphere_fallback").

**HOWEVER:** In the current uto reconstruction path, _improved_visual_hull is NOT called
(only InstantMesh and TripoSR are tried). The llow_fallback=False guard on the visual hull
prevents sphere production from that path. The sphere backend requires explicit ackend=sphere.

**PARTIAL BUG:** No TRIGENIX_ALLOW_SPHERE_FALLBACK environment variable gate exists.
The sphere CAN be invoked via the HTTP API with ackend=sphere in a future POST body
(currently the upload endpoint does not pass backend — it always uses "auto"). So the sphere
is practically gated today, but not explicitly by environment variable as the spec requires.
There is no labeled sphere result in API responses or history records.

### Bug B — Duplicated Camera Math

**STATUS: CONFIRMED — BUT ONLY IN RECONSTRUCTOR**

econstructor.py defines _camera_c2w and _project (the only inline camera math in the codebase).

processor.py has **NO** camera math at all. It does no projection.

So the bug is not "both files duplicate it" — it is "reconstructor.py defines its own projection
instead of a shared camera module." The design requires 	rigenix/geometry/camera.py to be the
single source of truth.

**Divergence vs. design:**
- econstructor._camera_c2w: CAM_DIST=1.80, Y-up, right-hand, -Z forward.
- Design spec camera: radius=1.5 (not 1.80), FOV=49.1° (not 36.9°). These differ.
- Zero123++ uses its own camera convention (radius=4.0 in _try_instantmesh).
- InstantMesh: get_zero123plus_input_cameras(batch_size=1, radius=4.0).
- THREE different camera models are in use: visual hull (dist=1.8, FOV=36.9°),
  InstantMesh Zero123++ cameras (radius=4.0), and TripoSR (its own internal cameras).

## Depth Usage Analysis

**DepthAnything IS invoked** for all 7 images (front + 6 views).
**Depth maps ARE saved** to disk as PNG files.
**Depth IS NOT consumed** by any geometry operation.

Evidence:
1. processor.estimate_depths() returns depths list — but the return value is ignored in
   process_image() (not stored in the returned dict).
2. econstructor._load_depth_maps() reloads them from disk but only for validation/logging.
3. In _improved_visual_hull(): depth maps are loaded, logged, then explicitly bypassed:
   `python
   logger.info("Loaded %d relative depth maps; skipping metric depth carving until calibrated", ...)
   `
4. mesh.metadata records "depth_maps_used_for_geometry": False.

**VERDICT: Bug A from the spec (depth not geometrically consumed) is CONFIRMED.**
This is the intentional "Option B" state — depth is correctly identified as relative-only and
excluded. However, there is no enforced contract — only a log message and metadata field.

## GPU Memory Management Analysis

**Zero123++:** Released after generate_views if not KEEP_PROCESSOR_MODELS_WARM.
Default is KEEP_PROCESSOR_MODELS_WARM=1 (env default keeps both warm).

**DepthAnything:** Released after estimate_depths if not KEEP_PROCESSOR_MODELS_WARM.

**TripoSR:** del meshes, scene_codes, model; gc.collect(); empty_cache(); ipc_collect()
inside _try_triposr. This is correct.

**InstantMesh:** No explicit del model after inference in _try_instantmesh. The local
variable goes out of scope when the function returns. GPU memory may not be freed immediately.

**Pattern:** load → infer → (conditional release). Mostly correct but not enforced by interface.

## Inline Camera Math Inventory

**econstructor.py** (the only file with projection math):
- _camera_c2w(az_deg, el_deg, dist=1.80) — spherical → rotation matrix + position
- _project(pts_world, az_deg, el_deg) — world pts → (u, v, depth, valid)
  - FOV_DEG=36.9, IMG_SIZE=320, CAM_DIST=1.80
  - Uses: f = S / (2 * tan(FOV/2)); R_wc = R_cw.T; depth = -pts_cam[:,2]

**InstantMesh/src/utils/camera_util.py** — get_zero123plus_input_cameras(radius=4.0)
  (separate, not audited here)

**Camera convention discrepancy:**
- Visual hull: dist=1.80, FOV=36.9°
- InstantMesh input cameras: radius=4.0
- Design spec target: radius=1.5, FOV=49.1°
All three differ. The design's camera.py will unify these.

## Additional Findings

### Output directory structure (actual vs. spec)
**Actual:** All files dumped flat into generated/<uuid_timestamp>/:
  masked.png, view_0..5.png, mask_0..5.png, depth_grey_0..6.png, depth_color_0..6.png,
  pose.json, view_poses.json, model.glb, model_print.stl, model_print.glb, model_ar.glb,
  model_game_lod0.glb, model_simulation.glb, model_collision.obj, quality_report.json,
  opening_mask_i.png, model_textured.glb, texture.png

**Required by spec:** Subdirectories input/, pose/, views/, masks/, depth/, normals/,
cameras/, reconstruction/, final/, reports/

This is a structural gap requiring directory reorganization.

### quality_report.json (actual vs. spec)
**Actual keys:** quality (sub-object with method/vertices/faces/watertight/etc.),
  profiles (asset profile dict)
**Required by spec (13 keys):** status, overall_score, pipeline_states, input, segmentation,
  views, depth, geometry_inputs, backend_provenance, render_back, consistency, printability, warnings

The current quality_report.json has none of the 13 required top-level keys.

### Camera convention for InstantMesh vs. visual hull
InstantMesh uses get_zero123plus_input_cameras(radius=4.0) — completely separate from the
_camera_c2w(dist=1.80) used by the visual hull. The two backends use incompatible camera
conventions. This is an architectural inconsistency requiring the unified camera module.

### Taubin smoothing sign
cleanup() calls ilter_taubin(mesh, lamb=0.18, nu=0.20, ...).
Spec says μ=-0.20 (negative). The trimesh API uses 
u for the second parameter which
corresponds to μ in Taubin's formulation. 
u=0.20 is POSITIVE — this means the mesh
will NOT shrink as intended by Taubin (which requires nu < 0). Minor bug.
